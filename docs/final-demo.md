# AstraVision 国赛最终版：启动与演示

版本：`national-cpu-parallel-20261020`。比赛日期：2026 年 10 月 24 日。
正式识别采用已验证的 80 ADU 流程，曝光拖尾重定位保留为实验工具。

## 拿到交付文件后

交付分成两个包：

- `star-chart-source-national-cpu-parallel-20261020.zip`：源代码、前端、配置、离线 Gaia 星表、测试、运行脚本与报告；满足源码压缩包 200 MB 限制。
- `star-chart-offline-national-cpu-parallel-20261020.zip`：完整演示包，包含上述程序、15 张官方 FITS、固定 CPU 镜像和验证证据；它与源码包分别提交，不适用源码包的 200 MB 限制。

先在比赛电脑准备 **Windows、Python 3.11 或更新版本、Docker Desktop（Linux containers、x86-64）及浏览器**。
Docker Desktop 必须已成功启动。首次安装这些软件需要提前完成；提供的 CPU 镜像可离线导入，
现场无需安装科学计算依赖、下载镜像、访问 Gaia 或连接外部网站。

将完整演示包解压到一个有写权限的目录，例如 `D:\AstraVision-final`。
路径含空格也可使用。PowerShell 进入解压后的 `offline-kit` 目录，执行：

```powershell
.\start.ps1
```

若脚本执行策略阻止本地脚本，可在该目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1
```

启动器检查冻结源码、官方数据和准确的镜像 ID。缺少镜像时，从随包
`runtime/star-chart-cpu.tar` 导入；校验失败会停止并说明原因。
通过后，在浏览器打开 `http://127.0.0.1:8765`。占用该端口时用 `.\start.ps1 -Port 8767`。
结束演示按服务器窗口中的 Ctrl+C。

CPU 默认自动选择最多 4 个进程。可在网页选择并行数量和执行方式；内存较小的设备建议先试 1 或 2。
本机 15 帧完整分析与出图导出从串行 90.76 秒降为 4 进程 48.14 秒，4 线程反而需要 172.01 秒，
因此优先使用多进程。性能需在比赛电脑实测；更多说明见 `docs/cpu-parallel.md`。

不修改 `src/`、`scripts/`、配置或随包星表。运行结果写入 `app/star-chart-recognization/output/`，
允许新增结果，不影响源码校验。要改进算法，应复制到开发目录，重新验证后制作新版本。
不要通过修改校验清单掩盖版本变化。

## 三分钟现场演示

比赛前已启动 Docker、运行预检并打开工作台；首次导入镜像不计入现场识别，务必提前完成。

| 时间安排 | 操作与说明 |
|---|---|
| 0:00–0:20 | 选择 `rst19`，指定评委要求的图像。默认 f7 表示第 8 张，勾选离线 Gaia 定标。说明本次使用全部 15 帧作识别与核验。 |
| 0:20 起 | 点击“开始识别”，展开真实日志。说明原始 FITS、背景建模、恒星配准、运动关联、曝光拖尾核验的顺序。 |
| 计算完成后约 30 秒 | 指出“本次运行结果”，展示恒星候选、运动候选和最暗候选；点选一条轨迹检查首/中/末原图切片与判据。 |
| 剩余时间 | 拖动时间滑块，展示目标坐标变化；下载轨迹 CSV，说明包含逐帧 UTC 与像素坐标。 |

f7 的已验证参考结果为 **12,842 个跨帧恒星候选、26 条运动候选、294 行目标位置**，
最暗恒星候选约 **14.53 等（Gaia G 参照估计）**。评委更换指定图像后，恒星统计和最暗候选可以变化。
运动候选没有身份标签，不能称 26 个已确认卫星。

背景固定为所选参考帧，时间滑块切换的是轨迹坐标，不能介绍成原始图像逐帧播放。
固定孔径可能漏掉长拖尾流量，右侧曲线也不能当作完整目标的精密光变曲线。

现场时间以比赛电脑实际排练为准。开发机计时和准确启动到导出的记录见
`docs/reports/cpu-parallel-2026-10-20.md`；上一版网页启动至导出的记录见
`docs/reports/final-release-2026-10-18.md`。不要把一次开发机运行当作所有机器的性能保证。

## 故障与备用路径

- Docker 未启动：启动 Docker Desktop，等待引擎就绪，再运行 `start.ps1`。
- 文件校验失败：从完整演示包重新解压到新目录；不要覆盖一半文件后继续运行。
- 工作台连接中断：查看服务器窗口，恢复服务后刷新。每次识别生成独立目录，已有结果不会被覆盖。
- 识别失败或被停止：展开日志排查。左侧历史结果明确标为“已保存结果”，只能作为注明时间与来源的备用展示。
- 网页打不开而计算环境正常：在 `app/star-chart-recognization` 下使用命令行运行，选择新输出目录：

```powershell
.\scripts\dr.ps1 python -m src.cli --input data/rst19 --reference-frame 7 --catalog docs/reference/rst19-gaia-dr3.csv --viewer --output output/manual-demo
```

此通用脚本默认使用本机 `star-chart:cpu` 标签；完整包按镜像 ID 导入后，可先执行：

```powershell
$env:SC_IMAGE = (Get-Content RELEASE.json -Raw | ConvertFrom-Json).image_id
```

需要单独预检时运行 `python scripts/verify_release.py --environment`。
只拿源码包时须自行把官方 15 张 FITS 放到 `data/rst19/`，并加载提供的 CPU 镜像。

科学性问题可用下列证据回答：

1. **如何防止用真值指导检测？** 推理层不接收注入参数或 `.DAT`；传递导入检查覆盖检测、配准、目标判决。注入真值只用于运行后的匹配与误差统计。
2. **为何不宣称真实准确率？** 官方完整目标真值缺失。注入回收有明确分母，但真实背景中未归属轨迹不能直接算 FP。Gaia G 也只是近似测光参照。
3. **创新体现在哪里？** 强调相对恒星背景的运动关联与曝光拖尾约束形成可审计判决，以及从消融到真实背景注入、失败定位的验证链；不把交互界面、常规 PSF 拟合或合成 100% Precision 单独称为算法突破。

注入实验使用与拟合相容的匀速拖尾和高斯 PSF，同一序列内的新区域仍不等于独立设备验证。
实验工具和原始评估计数随包保留；不因事后认出碎片就修改已发布回收率。
